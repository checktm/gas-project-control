# gas-project-control 要件定義

## 1. 目的

Google Apps Script（GAS）とGoogleスプレッドシートを利用し、社内の複数業務を管理できる軽量な業務管理Webアプリを構築する。

初期機能としてPM向けの進捗管理を対象としてきたが、進捗管理だけに限定せず、問い合わせ管理など周辺業務も同一基盤上で扱える構成とする。

単なる既存資料のWeb化ではなく、利用者が日常業務で以下を素早く把握・更新できることを目的とする。

- プロジェクト全体の進捗
- 遅延している工程・タスク
- 期限が近い工程・タスク
- 課題・リスク
- 次回アクション
- 担当者ごとの状況
- 進捗会議で確認すべき事項
- 顧客からの問い合わせ
- 問い合わせの対応状況・担当・期限
- 顧客とのメール履歴

## 2. 利用者

初期想定はPMおよび社内の問い合わせ対応担当者を主利用者とする。

将来的には以下の利用者も想定する可能性がある。

- プロジェクトメンバー
- 管理者
- 営業・顧客対応担当者
- 経営層・マネージャー

権限管理の詳細は、実際の利用形態を確認したうえで別途定義する。

## 3. 機能要件

### 3.1 プロジェクト管理

プロジェクト単位で以下を管理できること。

- プロジェクトID
- プロジェクト名
- 顧客名または案件名
- PM
- 開始日
- 終了予定日
- ステータス
- 全体進捗率
- プロジェクト概要・コメント

### 3.2 工程・タスク管理

プロジェクト配下に工程・タスクを登録できること。

初期候補項目は以下とする。

- タスクID
- 親工程または親タスク
- タスク名
- 担当者
- 計画開始日
- 計画終了日
- 実績開始日
- 実績終了日
- 進捗率
- ステータス
- 優先度
- 備考

実際に使用する項目は既存のPM進捗管理資料を確認して確定する。

### 3.3 ステータス管理

少なくとも以下の状態を表現できることを想定する。

- 未着手
- 進行中
- 完了
- 保留
- 遅延

「遅延」は入力値ではなく、日付と進捗から自動判定する方式を基本とする。

### 3.4 課題・リスク管理

プロジェクトまたはタスクに対して課題・リスクを管理できること。

初期候補項目は以下。

- 種別（課題 / リスク）
- 内容
- 重要度
- 担当者
- 対応期限
- 対応状況
- 次回アクション
- コメント

### 3.5 PMコメント・次回アクション

進捗会議や日常管理で使用するため、PMが自由記述できるコメントおよび次回アクションを保持できること。

### 3.6 ガントチャート

工程・タスクを期間軸で表示できること。

初期要件は以下。

- 計画期間を表示
- 実績または進捗状況を識別可能
- 今日の位置を把握可能
- 遅延タスクを識別可能
- プロジェクトまたは一定範囲に絞り込み可能

詳細は `docs/gantt-spec.md` を正本とする。

### 3.7 ダッシュボード

プロジェクト全体の状況を一画面で把握できること。

初期表示候補は以下。

- 全体進捗率
- 未完了タスク数
- 遅延タスク数
- 期限間近タスク数
- 未解決課題数
- 重要リスク数
- 今週の主要予定
- PMが確認すべき項目

既存進捗管理資料の内容を確認し、実務上必要なものに絞り込む。

### 3.8 顧客問い合わせ管理

特定の問い合わせ受付用メールアドレスに届くメールを自動取得し、問い合わせとして管理できること。

v0.1では以下を対象とする。

- 対象メールの定期自動取得
- Gmail message IDによる二重取込防止
- 送信元メールアドレスによる顧客担当者の完全一致判定
- メールドメインによる顧客候補判定
- 顧客を一意に判定できない場合の未確定状態保持
- Gmail thread IDを基準とした同一問い合わせへのメール履歴追加
- 問い合わせ一覧表示
- 顧客・担当者・自社担当者・状態・優先度・期限・次回対応の管理

メール1通を問い合わせ1件として固定せず、1問い合わせに複数メールを保持できる構造とする。

詳細は `docs/inquiry-management.md` を正本とする。

### 3.9 顧客管理

問い合わせ管理の基礎として、顧客会社と顧客担当者を分離して管理する。

- Customer: 顧客会社・組織
- CustomerContact: 顧客側担当者

表示名ではなく安定したIDで関連付ける。

## 4. 非機能要件

### 4.1 操作性

- ノートPCで主要な管理操作が行えること。
- 進捗会議中でも操作しやすいこと。
- 問い合わせ一覧から対応状況を素早く確認できること。
- 主要情報の確認に過度な画面遷移を要求しないこと。
- 一覧と編集の往復を少なくすること。

### 4.2 性能

初期段階では、小〜中規模のプロジェクト管理および問い合わせ件数を想定する。

GASおよびGoogleスプレッドシートの制約を考慮し、一行ずつの頻繁なサーバー通信を避け、可能な範囲でまとめて読み書きする。

メール取込処理は同一メールを安全に再実行できる設計を優先する。

### 4.3 保守性

- UI処理、業務ロジック、スプレッドシートアクセスを可能な範囲で分離する。
- Gmail取得処理と問い合わせ判定・保存処理を分離する。
- シート名・列番号などを画面処理へ直接散在させない。
- 項目変更時の影響範囲が分かりやすい構成とする。

### 4.4 データ整合性

- データ間の参照には安定したIDを利用する。
- 必須項目や日付の前後関係など、最低限の入力検証を行う。
- Gmail message IDによる二重取込を防止する。
- 顧客判定不能を異常終了扱いせず、未特定状態として保持できること。
- 更新失敗時に利用者が気付けること。

## 5. 想定データ保存先

Googleスプレッドシートを主なデータ保存先とする。

現在想定するシートは以下。

### 5.1 進捗管理

- Projects
- Tasks
- Members
- IssuesRisks
- Settings

### 5.2 問い合わせ管理

- Customers
- CustomerContacts
- Inquiries
- InquiryMessages

メール取込状態については、必要に応じて `MailImportState` を追加するか `Settings` で保持する。

必要以上にシートを細分化しない。

## 6. 初期対象外

現時点では以下を必須機能としない。

- 高度な工数原価管理
- 請求管理
- 契約管理
- 複雑なワークフロー承認
- 外部顧客向けポータル
- 高度な権限制御
- Jira等との双方向同期
- 管理画面からの問い合わせメール返信送信
- AIによる問い合わせ要約・分類・優先度判定
- 添付ファイル管理

必要性が確認された場合に追加検討する。

## 7. 未確定事項

以下は実際の運用を確認して確定する。

1. 現在の進捗管理項目と必須項目
2. プロジェクト・工程・タスクの階層
3. 進捗率の入力方法・算出方法
4. 課題とリスクの管理方法
5. 進捗会議で必要な集計値
6. 担当者・組織の持ち方
7. 複数プロジェクトを横断した表示の必要性
8. 更新履歴の必要性
9. 権限管理の必要範囲
10. スマートフォンで必要な操作範囲
11. 問い合わせ取得対象メールアドレス
12. 対象アドレスの実体（Workspaceユーザー / エイリアス / Google Group / 転送等）
13. メール取込間隔
14. 自社送信メールを問い合わせ履歴へ含めるか
15. 既存顧客マスタの有無

## 8. 次の作業

問い合わせ管理については、`docs/inquiry-management.md` を基準に以下を進める。

1. Customers / CustomerContacts / Inquiries / InquiryMessages のシート設計・作成
2. 対象メールアドレスと取得方法の確定
3. メール取込処理の実装
4. 顧客自動判定の実装
5. 問い合わせ一覧・詳細UIの試作
6. 実運用確認後に返信・AI支援などを段階追加
