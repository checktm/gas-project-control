# ユーザマスタ・アクセス制御 設計 v0.1（実装前仕様）

## 目的と前提
- 対象: gas-project-control の顧客Google Workspace環境。利用者は全員同一Google Workspaceドメイン。
- Google Workspace認証を利用し、Usersに登録された有効ユーザーだけが業務データ/APIを利用できる。
- 既存のMembersは問い合わせ担当者マスタであり、ログイン権限とは区別する。
- 顧客Apps ScriptとSpreadsheetは顧客環境に置き、顧客の運用アカウントでデプロイ・Gmail取込トリガーを実行する。

## Webアプリと本人確認
- Webアプリのaccess=DOMAIN、executeAs=USER_DEPLOYINGを基本とする。既存 MYSELF から変更が必要。
- Session.getActiveUser().getEmail() を取得し、trim/lowercaseで正規化する。**Session.getEffectiveUser() は利用者識別に使わない**（デプロイ実行者となる）。
- メールアドレスが空文字、ドメイン不一致、Users未登録、active=falseの場合はfail closedで拒否。クライアントが送ったemail/role/userIdは信用しない。
- 仕様上同一ドメインではメール取得が可能なことがあるが、実環境の公開設定・別ユーザーで検証してからアクセス制御を有効化する。
- Googleアカウント本人確認とUsers照合はそれぞれ必要。公開範囲DOMAINだけでは同ドメインの未許可者を拒否できない。

## Usersシート
- user_id（安定ID、USR接頭辞等）
- user_name（必須、表示）
- email（必須、同ドメイン、正規化した一意のメールアドレス）
- role（ADMIN / USER）
- active（真偽）
- member_id（任意、既存Membersの有効なIDのみ）
- updated_at（日時）
- 編集画面は既存マスタ管理にユーザータブを追加、ADMINのみ表示/操作。
- 同じメールの重複を禁止。ADMINの最後の一人を無効化・降格・削除不可。物理削除せず無効化。
- 初期管理者登録はセットアップを実行する運用管理者の明示的メールアドレスを検証し、管理者のみがApps Scriptエディタから行う。Users空を理由に自動で全員許可する挙動は禁止。

## 権限 v0.1
- ADMIN: 既存業務操作に加えてUsers管理とシステム設定更新。
- USER: ダッシュボード、問い合わせ閲覧・編集・分離・対象外指定・メール取込・返信、AI支援、顧客/担当者/メンバー/分類の通常マスタ更新。Users管理およびシステム設定更新は不可。
- 権限は各リクエストでサーバー側で評価し、UIの非表示だけで代用しない。将来細かいロールを追加できるよう権限チェックを集中化する。

## API・ページの境界
- doGet: ユーザー照合後に業務HTMLを返す。拒否時は業務データ/設定値を埋め込まない「アクセス権がありません」ページを返す。
- 公開されるgoogle.script.runエントリポイントは全部列挙し、読取・更新・メール送受信・AI・マスタ・設定など各エントリに認可チェックを追加する。HTML取得制御だけでは不十分。
- getAppConfigなど設定を返すAPIも対象。include等の内部関数がクライアントから呼べない/使えないよう見直す。Apps Scriptの末尾_による非公開関数規約を利用し、内部関数は適切に区別する。
- 定期Gmail取込、初期化、診断、管理用関数は対話Web APIとは区別し、Web側から直接無制限に呼べる入口を作らない。特権トリガーと業務利用者APIの入口を分離する。
- 権限判定時にSpreadsheetを開くため、スプレッドシートの失敗時は許可しない。認可前にGmail取得/書込/AI呼出をしない。
- 利用者にはSpreadsheet/Apps Scriptの編集権限を共有しない。Webアプリ閲覧URLのみを配布する。編集権限があるとUsersシートやソースによるアクセス制御を迂回できる。

## 初期導入・移行
1. 開発環境で別Workspaceユーザーを用いてactiveUserメール取得と同ドメイン公開設定を試験。
2. Usersシートと管理者初期登録（ブートストラップ）を用意。
3. サーバー公開関数の棚卸しを完了し、認可チェックを追加。
4. 管理画面UIとアクセス拒否画面を追加。
5. 開発環境で未登録/無効/USER/ADMIN、Gmail送信、取込トリガー、管理者ロックアウト防止を確認。
6. 顧客環境のバックアップと初期管理者登録を先に実行後、Webアプリをドメイン内アクセスへ変更。既存Gmail取込トリガーを維持。
- 新しいデプロイ設定と新しいスコープが必要となる場合は明示する。
- 顧客環境へのコード反映はユーザーが指示するまで実施しない。

## 要確認 / リスク
- 顧客ドメインで実際にSession.getActiveUser().getEmail()を取得できること。取得不能なら同方式を本番適用しない。
- Gmail送受信はUSER_DEPLOYINGアカウントを利用すること。送信者はアクセス利用者本人と一致しない場合がある。
- APP_CONFIG.spreadsheetId等、開発・顧客個別設定は引き続き保護する。
- スプレッドシートの直接共有者はアプリの権限体系の対象外であり、Google Drive共有権限も別途制御する。

## メンバーマスタからのユーザー取り込み（2026-10-19）
- マスタ管理の「ユーザー」タブで管理者が「社内メンバーから追加」を実行できる。
- Membersのうち、`active=TRUE`・有効な氏名/メールアドレス・管理者と同一メールドメイン・Users未登録の候補だけを選択表示する。
- チェックされた対象を `USER` ロール、`active=TRUE`、`member_id` 紐付けで新規登録する。既存Usersの権限/activeは変更しない。CustomerContactsは対象にしない。
- 取込を実行できるのは現時点でUsersに登録済みのADMINのみ。初期ADMINは顧客運用担当者がセットアップ時にUsersへ登録する。
- この段階はユーザー管理と取り込みUIまで。GAS Webアプリ全体の認可ガード・公開設定変更・別アカウント検証は未完了であり、一般利用者の全業務APIへのアクセス拒否はまだ保証されない。
