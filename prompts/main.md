# gas-project-control 開発方針

この文書は、`gas-project-control` の設計・実装・レビューで共通して守る基本方針です。

## 1. 正本

- 最新の `main` ブランチを基準に作業する。
- 要件の正本は `docs/requirements.md` とする。
- 実装前に、対象機能に関係する既存ドキュメントとソースを確認する。
- 仕様変更時は、コードだけでなく関連ドキュメントも更新する。

## 2. 開発目的

このアプリの目的は、既存のPM進捗管理資料を単純にWeb化することではない。
PMが日常業務・進捗会議・問題把握に使いやすい形へ整理し、入力負荷を抑えながら進捗・遅延・課題・リスクを把握できることを重視する。

## 3. 技術方針

- Google Apps Script（GAS）をアプリ基盤とする。
- Googleスプレッドシートを主なデータ保存先とする。
- UIはGAS HTML Service上のHTML / CSS / JavaScriptで構築する。
- Google Workspaceとの連携は、GASの標準機能または必要性が明確なAPIのみ利用する。
- 将来の保守を考慮し、画面、業務ロジック、スプレッドシート入出力の責務を可能な範囲で分離する。

## 4. 設計原則

- 既存資料の項目・運用を確認してからデータ構造を決める。
- 既存資料のすべてをそのまま再現するのではなく、PM業務上必要な情報を整理する。
- 同じ意味・同じ動作のものだけを共通化する。
- 将来使うかもしれないという理由だけで過度な汎用化をしない。
- 入力項目を増やす場合は、PMの管理負荷に見合う価値があるか確認する。
- スプレッドシートの列構成をUI都合だけで頻繁に変更しない。

## 5. UI / UX方針

- ノートPCで主要情報を把握できることを優先する。
- 進捗会議中に操作しても迷いにくいことを重視する。
- 一覧性を保ちつつ、詳細編集に必要な操作数を減らす。
- 遅延、期限超過、課題、リスクは視覚的に判別しやすくする。
- 不要なページ遷移やモーダルを増やさない。
- スマートフォン対応は初期段階では閲覧性を優先し、入力操作は必要性に応じて検討する。

## 6. データ方針

- 可能な限り安定したIDを持たせ、表示名をキーとして参照しない。
- 日付、進捗率、ステータスなどは保存形式を統一する。
- 集計値は、必要に応じて元データから再計算できる構造を優先する。
- 手作業で修正されたスプレッドシートも想定し、読み込み時の最低限の検証を行う。

## 7. 実装時の確認事項

実装前に以下を確認する。

1. 最新 `main`
2. `prompts/main.md`
3. `docs/requirements.md`
4. 対象機能に関係する設計資料
5. 対象機能に関係する既存ソース

大きな仕様変更、シート構造変更、既存データ移行が必要な場合は、影響範囲と移行方法を先に整理する。

## 8. 現時点の優先順位

1. 現在使っているPM進捗管理資料の把握
2. 管理対象・項目・画面構成の整理
3. データ構造の確定
4. 画面試作
5. GAS実装
6. 実運用での改善
