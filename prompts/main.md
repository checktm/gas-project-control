# gas-project-control 開発方針

この文書は、`gas-project-control` の設計・実装・レビューで共通して守る基本方針です。

## 1. 正本

- 最新の `main` ブランチを基準に作業する。
- 要件の正本は `docs/requirements.md` とする。
- 各機能の詳細仕様は対応する `docs/*.md` を正本とする。
- 実装前に、対象機能に関係する既存ドキュメントとソースを確認する。
- 仕様変更時は、コードだけでなく関連ドキュメントも更新する。

## 2. 開発目的

このアプリは、PM進捗管理だけに限定した専用ツールではなく、Google Workspaceを活用した軽量な業務管理基盤として育てる。

初期機能として進捗管理を持ち、問い合わせ管理など周辺業務も同一基盤上で扱えるようにする。

単に既存資料やメール運用をWeb化するのではなく、利用者が日常業務・進捗会議・問い合わせ対応・問題把握に使いやすい形へ整理し、入力負荷を抑えながら必要な情報を把握できることを重視する。

## 3. 技術方針

- Google Apps Script（GAS）をアプリ基盤とする。
- Googleスプレッドシートを主なデータ保存先とする。
- UIはGAS HTML Service上のHTML / CSS / JavaScriptで構築する。
- Google Workspaceとの連携は、GASの標準機能または必要性が明確なAPIのみ利用する。
- 将来の保守を考慮し、画面、業務ロジック、外部サービス取得処理、スプレッドシート入出力の責務を可能な範囲で分離する。
- Gmail取得処理と問い合わせ判定・保存処理は分離する。

## 4. 設計原則

- 既存資料・既存運用を確認してからデータ構造を決める。
- 既存運用のすべてをそのまま再現するのではなく、業務上必要な情報を整理する。
- 同じ意味・同じ動作のものだけを共通化する。
- 将来使うかもしれないという理由だけで過度な汎用化をしない。
- 入力項目を増やす場合は、管理負荷に見合う価値があるか確認する。
- スプレッドシートの列構成をUI都合だけで頻繁に変更しない。
- 自動処理は再実行可能性と二重登録防止を重視する。
- 自動判定できないデータを無理に推測して確定せず、未確定状態として保持できる構造を優先する。

## 5. UI / UX方針

- ノートPCで主要情報を把握できることを優先する。
- 日常業務や会議中に操作しても迷いにくいことを重視する。
- 一覧性を保ちつつ、詳細編集に必要な操作数を減らす。
- 遅延、期限超過、課題、リスク、未対応問い合わせは視覚的に判別しやすくする。
- 不要なページ遷移やモーダルを増やさない。
- スマートフォン対応は初期段階では閲覧性を優先し、入力操作は必要性に応じて検討する。

## 6. データ方針

- 可能な限り安定したIDを持たせ、表示名をキーとして参照しない。
- 日付、進捗率、ステータスなどは保存形式を統一する。
- 集計値は、必要に応じて元データから再計算できる構造を優先する。
- 手作業で修正されたスプレッドシートも想定し、読み込み時の最低限の検証を行う。
- Gmail連携では Gmail message ID / thread ID を保存し、二重取込と誤結合を防ぐ。
- 顧客判定不能はエラーではなく、未特定状態として扱う。

## 7. 実装時の確認事項

実装前に以下を確認する。

1. 最新 `main`
2. `prompts/main.md`
3. `docs/requirements.md`
4. 対象機能に関係する設計資料
5. 対象機能に関係する既存ソース

大きな仕様変更、シート構造変更、既存データ移行が必要な場合は、影響範囲と移行方法を先に整理する。

## 8. 現時点の優先順位

1. 問い合わせ管理v0.1の仕様確定
2. Customers / CustomerContacts / Inquiries / InquiryMessages のデータ構造
3. 対象メール取得・二重取込防止
4. 顧客・担当者自動判定
5. 問い合わせ一覧・詳細UI
6. 既存の進捗管理機能との段階的連携
7. 実運用での改善

問い合わせ管理の詳細仕様は `docs/inquiry-management.md` を参照する。
